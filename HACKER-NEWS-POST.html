Six production-shaped apps, one Rails codebase, zero SPA

A field report on building a kanban board, a realtime chat, a live ops dashboard, a polling app, a spreadsheet, and a music player — all on one Rails 8 + Hotwire stack, with no React, no client-side state model, and no JSON API. Here's what each one proves, the code that makes it work, and where the approach actually bites.

By the Levelbrook engineering team ~20 min read Live: demo.levelbrook.com

"Rails can't do modern, app-like UX — you'll end up rewriting the front end in React." We hear this in almost every Rails consulting conversation, and we've never fully agreed with it. So instead of arguing, we built the counter-argument: a switcher that opens into six distinct, realtime, production-shaped products, every one of them server-rendered HTML over the wire.

Not six variations on a to-do list. Six genuinely different problem domains, each chosen because it exercises a different corner of the modern Hotwire stack — drag-and-drop with live multi-user sync, optimistic UI, background-job progress streaming, server-computed spreadsheet formulas, and audio that survives navigation. One Rails app. One SQLite file. One themeable shell. 102 tests. Deployed to a single box with Kamal.

You can click through all of them right now: demo.levelbrook.com. The rest of this post is the interesting part — how, and the judgment calls that actually matter.

The thesis isn't "Hotwire instead of React." It's "the server already has the HTML — stop rebuilding it on the client."

The shape: one shell, six products

The whole portfolio is a single Rails app. The root URL is a gallery; each card opens an app that re-skins the chrome and mounts its own models, controllers, and Stimulus controllers. We didn't want six near-identical apps in different colors, so each lives in its own domain and namespace.

The re-skinning is almost embarrassingly cheap. There's a registry of apps:

# app/lib/showcase.rb
module Showcase
  App = Data.define(:key, :name, :tagline, :accent, :accent_soft, :glyph, :primitives)

  APPS = [
    App.new(key: :workspace, name: "Workspace", accent: "#c8402f", …),
    App.new(key: :pulse,     name: "Pulse",     accent: "#4f46e5", …),
    # …four more
  ]
end

The controller infers which app it belongs to from its path (namespaced controllers resolve from their namespace; everything else is the workspace), and the layout themes itself by overriding a single CSS custom property on a wrapper:

<%# app/views/layouts/application.html.erb %>
<div class="flex min-h-full"
     style="--color-accent: <%= current_app.accent %>;
            --color-accent-soft: <%= current_app.accent_soft %>;">
  <%= render "shared/app_sidebar" %>
  …
</div>

Every view in every app references var(--color-accent) instead of a hard-coded color, so one inline style restyles an entire product. Adding a seventh app is one registry row plus its own views — the shell needs no changes. This is the kind of leverage that makes a small team move fast, and it's the same instinct we bring to client codebases: find the one seam that makes the next ten features cheap.

The six, and what each one proves

01 · Workspace — project delivery

A Jira-grade board where drag-and-drop syncs across browsers

SortableJSbroadcasts_refreshesTurbo morphFrame drawerinstant inline edit

Drag-and-drop with live multi-user sync is the canonical "you need a SPA for that" feature. Here it's a thin Stimulus wrapper around SortableJS, one PUT endpoint, and a single line on the model:

class Project < ApplicationRecord
  has_many :columns
  broadcasts_refreshes   # ← that is the entire realtime layer
end

On drop, the browser PUTs the card's new column and position. The controller saves and returns 204 No Content — it does not re-render anything. The broadcasts_refreshes line fires a refresh over Action Cable; every connected client (including the one that dragged) morphs its DOM with idiomorph, so only the moved card changes. Scroll position and focus are preserved.

The part that bit us

Morphing fights drag. If a broadcast lands mid-drag, idiomorph tries to rewrite the node SortableJS is holding. The fix is to keep drag state DOM-resident and let the server be the single source of order: return 204, never echo the drag back to its originator, and let the morph reconcile everyone uniformly.

The latency insight (inline edit)

Click-to-edit usually does a round trip just to enter edit mode (GET the form, swap the frame). That network hop is the lag you feel. We render the display and the edit form together and toggle to the input client-side instantly; submitting still hits the server, which returns the updated field and re-broadcasts. Snappy on click, authoritative on save — and the GET still works as a no-JS fallback.

02 · Cadence — team comms

Campfire-style chat: presence, typing, append streams, optimistic reactions

broadcast_append_tobroadcast_replace_toAction Cable presenceoptimistic UI

Chat is where the morph-everything default is wrong, and knowing that is the actual skill. A new message shouldn't re-render the whole conversation; it should append. A reaction shouldn't append; it should replace one message. So the model uses three different broadcast verbs deliberately:

class Message < ApplicationRecord
  after_create_commit { broadcast_append_to  channel, target: "messages",    partial: "messages/message" }
  after_update_commit { broadcast_replace_to channel, target: dom_id(self), partial: "messages/message" }
end

Presence and typing ride raw Action Cable — they're ephemeral, non-DOM state, so streaming HTML for them would be the wrong tool. Reactions are optimistic: the count bumps in the browser the instant you click, then the server persists it and broadcast_replace_to reconciles the number for everyone.

The rule we keep

Morph for complex pages, append for feeds, replace for a single item, raw cable for ephemeral state. Reaching for the right one is judgment; defaulting to "refresh everything" is how realtime Rails apps get slow.

03 · Pulse — monitoring

A live ops dashboard with morphing SVG charts and a streamed deploy bar

server-rendered SVGActive Job → Turbo Streamlazy framesno charting JS

Everyone assumes dashboards need a charting library and a polling loop. The sparklines here are server-rendered SVG — a helper turns a list of samples into a polyline — and they update by morph when new data arrives. No Chart.js, no setInterval.

The headline feature is a deploy that streams its own progress, which is the canonical background-job → browser loop with no polling:

class Pulse::DeployJob < ApplicationJob
  def perform(service_id)
    [6, 18, 33, 49, 64, 78, 91, 100].each do |pct|
      Turbo::StreamsChannel.broadcast_replace_to "pulse_dashboard",
        target: "deploy_status", partial: "pulse/dashboard/deploy_status", locals: { pct: }
      sleep 0.45
    end
  end
end

Open the dashboard in two tabs, run a deploy in one, watch the bar fill in both. Below the fold, a "recent events" panel is a lazy Turbo Frame — deferred to the server so first paint stays fast.

04 · Ballot — events

Slido-style live polls where tallies morph across every client

optimistic + reconcilebroadcast morphmorph-survivalCSS-bar charts

Vote and the bar bumps immediately on your screen; the server records it, touches the room, and broadcasts_refreshes morphs the authoritative tallies onto everyone. This one hides the subtlest lesson in the whole project, and it's worth slowing down for.

The bug that teaches the lesson

A broadcast re-renders the page server-side, in a background job, with no session. So "which option you picked" — a per-user, per-browser fact — cannot come from the broadcast. If you render it server-side it'll be wrong for everyone but the last voter, and the next morph will wipe it anyway. The answer is that per-user state must live on the client and survive the morph. Stimulus makes that clean, because a controller's connect() runs again after every morph:

// poll_controller.js — re-applies *this browser's* vote after each morph
connect() { this.applyVoted() }

applyVoted() {
  const choice = localStorage.getItem(this.storageKey)
  if (!choice) return
  this.optionTargets.forEach(el => el.disabled = true)   // lock + highlight my pick
}

The tallies are shared and authoritative; the "you voted for X" highlight is local and morph-proof. That split — global truth on the server, personal state on the client — is the whole game in collaborative UIs, and it's the kind of thing you only get right after you've shipped a few of them.

05 · Grid — data

An Airtable-lite spreadsheet with server-computed formula cells

frame-scoped cell editserver formula recalcmorphno spreadsheet engine

Click any cell, edit it inline, blur to save. The Total column and the grand total are formula cells — never stored, always derived:

class Grid::Row < ApplicationRecord
  belongs_to :sheet, touch: true
  def total = qty * unit_price          # the "formula", computed on the server
end

Editing a cell touches the sheet, which broadcasts_refreshes; idiomorph then updates only the cells whose text actually changed — the edited cell, its row total, the grand total. A spreadsheet, recalculating live across collaborators, with no client-side formula engine and no React.

06 · Spindle — media

A player that keeps playing while you browse the whole app

data-turbo-permanentWeb AudioView Transitions

"The audio keeps going as you navigate" is a Spotify-grade feature that's genuinely hard in a naive SPA and almost free in Hotwire. The player lives in the layout with data-turbo-permanent, so Turbo never tears it down between navigations — its Stimulus controller (and the Web Audio graph it owns) is created once and outlives every page change.

Track rows can't call the permanent controller directly, so they dispatch a window event it listens for — which is exactly what lets the page re-render while the music keeps playing:

// a track row just announces itself; the permanent player takes over
window.dispatchEvent(new CustomEvent("spindle:play", { detail: track }))

And about the audio: rather than ship copyrighted files, every track is synthesized live in the browser with the Web Audio API — real chord progressions (voiced as open fifths and octaves so they're always consonant), shaped by a per-track texture. It's intentionally simple music; the point is the persistence, and audio is only ever started by you. Album art animates between pages with the View Transitions API, feature-detected so unsupported browsers just… navigate.

What ties it together

A few principles run through all six, and they're the same ones we apply on client engagements:

Morph-first, append when it matters

The default realtime strategy is broadcasts_refreshes + idiomorph, because it's one line and it preserves scroll/focus. We drop to surgical broadcast_append_to / replace_to only where a feed or a single item demands it (chat, reactions). Most "you need a SPA" UIs are really just "you need to morph the DOM well," and Turbo 8 does.

Optimistic on the client, authoritative on the server

Votes, reactions, and drags all give instant feedback, fire the request, and let the broadcast reconcile. The server is always the source of truth; the client just refuses to feel slow while it waits.

Progressive enhancement, for real

Every interaction degrades. Search is a normal GET form before it's a combobox. The issue drawer is a Turbo Frame, but /issues/:id is a real page. Inline edit falls back to a GET'd form. Turn off JavaScript and the apps still work — they just stop being instant. That's not nostalgia; it's resilience and accessibility you get for free when the server owns the HTML.

The economics

No client state model to keep in sync. No serializers, no API versioning, no hydration step, no second rendering path. One place to render each piece of UI, and it's the place that already has the data. For a small team or a lean budget, that's not a constraint — it's the advantage.

Where this approach actually bites

We don't think Hotwire wins every argument, and pretending otherwise would be the tell that we haven't shipped it. Honest limits:

  • It's a demo, deployed honestly. One Hetzner box, SQLite, Solid Queue running inside Puma, Kamal for deploys. That's a great fit for this — and the wrong topology for a high-availability product. The patterns scale; this deployment isn't meant to.
  • Refresh-broadcasts re-render. broadcasts_refreshes re-renders a page fragment server-side and morphs it. On very high-churn screens you'll want surgical streams instead — which is exactly why chat uses append, not refresh. The default is great until it isn't, and knowing the line is the job.
  • Some UI genuinely wants a client framework. A canvas editor, a 10k-row virtualized grid, an offline-first app — reach for the right tool, ideally as an island, not a full rewrite. "Hotwire first" is a default, not a religion.
  • The synth is a party trick. It exists to prove the persistence point without shipping audio files. Real product, real tracks.
