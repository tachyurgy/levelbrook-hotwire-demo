Executive Audit

What already works
  • Modern Rails 8 app using Hotwire, importmap, Propshaft, Tailwind, Solid Cable, Solid Queue, and Solid Cache.
  • Coherent workspace app: dashboard, projects, kanban board, issue modal, chat, search, activity feed, command palette, and intake form.
  • Strong Hotwire coverage: broadcasts_refreshes, model broadcasts, lazy frames, frame-scoped inline edit, raw Action Cable, typing, presence, permanent player, and View Transition meta tags.
  • Controller code is generally small and lifecycle-aware. Sortable, chat observer, debounce, typing, presence, player, toast, and modal controllers all clean up timers/subscriptions/observers.
What blocks it from being impressive
  • README is stale. It describes old /board and /story demos, but the app now exposes /projects, /channels, /search, /activities, and /signups.
  • The core realtime board proof may be incomplete. Same-column reorder uses update_column and may not touch the project, so other connected clients can miss the morph refresh.
  • The app explains techniques too early. Captions are useful, but the demo needs visible before/after proof: embedded second client, seeded guided flow, and obvious live updates.
  • Some modules are present but underused. Toast helper exists but is not visibly triggered. Activity feed is synthetic and cached, not live. Persistent player proves state, but it needs stronger purpose or a clearer exhibit.
  • Presence is weak as a sales proof. Default identity means many browsers can appear as the same person. It needs a quick identity switcher or demo-client labels.
Verdict

The app is much closer to a good Hotwire showcase than the README suggests. The work now is not to add ten more disconnected tricks. The work is to tighten the proof path, fix the realtime correctness gaps, and make every advanced feature visible in a coherent client story.

Hiring Demo Story

The demo must answer one question: "Can Levelbrook build modern app UI in Rails without defaulting to React?" The flow should be scripted and visible:

  1. Open the dashboard. It looks like a real delivery workspace, not a marketing page.
  2. Open the board with a built-in second-client preview. Drag a card and watch the preview morph in place.
  3. Open an issue drawer. Edit title/status/assignee through Turbo Frames and add a comment that streams live.
  4. Open team room. Send a message, see append-stream behavior, presence, and typing over raw Action Cable.
  5. Use command palette and search. Show server-rendered results, keyboard nav, URL/history correctness, and no client search index.
  6. Use intake validation. Blur invalid fields and show server-authoritative field errors streamed back.
  7. Finish with code receipts. Link to a short "How it works" page that maps each feature to files and Hotwire primitives.

Priority Build Plan

Phase 0: Correct the truth, 0.5 day

  • Rewrite README.md to describe the current Levelbrook Delivery Workspace, not the old board/story app.
  • Add a docs/hotwire-proof-map.md linking each visible feature to files, tests, and referenced repo patterns.
  • Rename routes/copy consistently: "Levelbrook", not mixed "Lebrook"/"Levelbrook". Keep this file as the planning artifact if the misspelling was intentional shorthand.

Phase 1: Fix the core board proof, 1 day

  • Make Issues::PositionsController#update touch or broadcast the project after every reorder, including same-column reorders.
  • Replace update_column with a deliberate persistence path that keeps callbacks/broadcast intent explicit, or call issue.project.touch! once at the end of the transaction.
  • Add tests that verify a same-column reorder causes the project refresh broadcast path. If system tests are practical, add a two-session board sync test.
  • Add WIP-limit enforcement or remove the seeded issue promising it. If built, reject the move, stream a toast, and let morph reconcile the card position.

Phase 2: Make the demo self-proving, 1-2 days

  • Add /demo or make project show include a collapsible second-client preview iframe of the same board.
  • Add a guided proof rail with 5 concrete actions: drag card, open drawer, edit field, send comment, reset board.
  • Fire real toasts from reset, WIP rejection, successful inline edit, and signup success so the stream side-channel is not just unused infrastructure.
  • Add identity switching in the chat sidebar so two browsers can appear as different people without private browsing tricks.

Phase 3: Turn features into a coherent product, 2-3 days

  • Upgrade issue modal to a right-side drawer while preserving the lazy Turbo Frame and full-page fallback.
  • Make activity persisted or event-backed. Issue moves, comments, and messages should create activity entries that stream-prepend live, then paginate by lazy frames.
  • Improve search into workspace search: assignee filter, status filter, priority filter, sort, highlighted snippets, and frame-scoped pagination.
  • Add a server-driven background job exhibit: "Generate client status report" streams progress through Solid Queue and Turbo Streams, then exposes a download/result.

Phase 4: Add senior-level differentiators, 2-4 days

  • Add shared-element View Transitions from issue card to drawer/detail. Keep reduced-motion handling and unsupported-browser fallback.
  • Add optimistic UI on one small action, such as starring an issue or acknowledging an activity item, then reconcile via morph.
  • Add presence-aware edit locks on issue fields: "Ada is editing title" appears, releases on disconnect, and survives refresh correctly.
  • Optionally add a small Hotwire Native bridge exhibit only if it can be honestly demonstrated with path configuration and bridge controllers.

Acceptance Criteria

Visitor proof

  • A prospect can see realtime board sync in one browser within 15 seconds.
  • Every feature has a believable workspace reason, not just a technique caption.
  • No dead promises in seeded data or README.
  • Mobile and desktop layouts remain usable for board, chat, search, and drawer.

Engineer proof

  • Tests cover same-column reorder broadcast, message/comment streams, field validation, and search behavior.
  • Stimulus controllers use targets/values/classes, clean up in disconnect(), and avoid page-controller sprawl.
  • Streams are scoped to records, not global channels for private data.
  • App can be deployed and seeded from documented commands.
