Optimistic UI, authoritative morph

A live-polls and audience-Q&A app where every vote feels instant for the person tapping — yet the numbers everyone sees stay correct, reconciled by the server over a single broadcast. Almost no custom JavaScript.

optimistic UI broadcast morph tallies CSS-bar charts no charting JS

A build note from Levelbrook Consulting — senior Ruby on Rails & Hotwire.

Ballot is one of six self-contained Hotwire apps that share a single Rails 8 codebase in our showcase. It does two things you have seen at every conference and all-hands: live polls you vote in and watch tally in real time, and an audience Q&A where people post questions and upvote each other's — the list re-sorting itself as votes land. Both update for every connected browser instantly.

The interesting part is not what it does — it's how little code does it, and the discipline behind that. There is no charting library. There are exactly two small Stimulus controllers. The realtime wiring on the page is one line. And underneath sits a pattern worth naming and stealing: optimistic UI on the client, authoritative reconciliation by the server, delivered as a morph. This post walks the whole loop end to end, straight from the code.

The shape of the thing

Ballot lives under a Rails namespace. The models are Ballot::Room, Ballot::Poll, Ballot::Option, and Ballot::Question, and they back tables prefixed ballot_. That namespacing is deliberate: the showcase mounts six apps in one Rails app, and prefixing keeps Ballot's tables and classes cleanly partitioned from everyone else's.

A room is the unit of liveness. It has_many polls and questions, and it is the single source of broadcasts:

Two lines carry most of the architecture. The questions association is ordered upvotes_count: :desc — so "the most-upvoted question floats to the top" is a database concern, not a JavaScript one. And broadcasts_refreshes makes the room the broadcast source: any commit that touches it emits a single <turbo-stream action="refresh">, and every subscribed browser re-fetches the page and morphs its DOM to match.

The poll and option models are just as thin. A poll knows its total; an option knows its share of that total.

Note touch: true on both belongs_to declarations. An option belongs to a poll which belongs to a room. When an option's vote count changes, the touch bubbles up the chain to the room — which is exactly the model that broadcasts. The questions model carries the same belongs_to :room, touch: true. This is the wiring that turns "a counter went up somewhere" into "every screen in the room updates," with no hand-written broadcast code anywhere.

The signature pattern, traced through one vote

Here is the loop you should hold in your head. A person taps an option. Three things happen, in this order:

  1. The browser updates itself immediately — recomputing every bar in that poll from the new total. This is the optimistic step; it is the reason the tap feels instant.
  2. The choice is recorded in localStorage, and a POST goes to the server.
  3. The server increments the real counter, touches the room, and replies 204 No Content — no body. The room's broadcasts_refreshes then morphs the authoritative tallies onto every open browser, including the one that just voted.

Look at how little the server does. The whole endpoint:

Three meaningful lines: find the option, increment! the counter, room.touch. The response is head :no_content — a deliberate 204. The controller renders no UI at all. Every pixel that changes on every screen arrives through the refresh broadcast. The POST is a write; the broadcast is the read. Keeping those separate is what makes this so clean: there is exactly one code path that produces the on-screen tallies (the page template), and it runs for everyone the same way.

Now the client half. The poll Stimulus controller does the optimistic recompute:

Crucially, the optimistic update does not just bump one number — it recomputes every bar from the new total, exactly as the server will. Add a vote to one option and the others' percentages all drop slightly; the controller mirrors that so the local picture is internally consistent the instant the tap registers, not just plausibly close. The POST goes out via @rails/request.js, and then the controller is done. It is not waiting on the response to update anything.

Why this feels instant and stays correct. The voter sees their tap reflected in a single frame, with zero network latency in the critical path — the optimistic recompute runs synchronously on click. Meanwhile everyone else (and the voter, a beat later) gets the server's authoritative numbers via the morph. If the optimistic guess and the truth ever diverge — two people vote at once, the local count drifts — the morph silently corrects it. Optimism buys perceived speed; the broadcast buys correctness. Neither compromises the other.

Morph-survival of per-client state

This is the subtle bit, and the part most teams get wrong when they first reach for broadcasts_refreshes.

The refresh broadcast replaces the DOM. It is the server's rendering of the page — and the server has no idea that this particular browser already voted. The server-rendered option buttons come back enabled, un-highlighted, generic. So how does the "you voted for this one, the buttons are locked" state survive a full server-driven DOM replace?

It survives because Turbo morphs rather than wholesale-replaces, and morphing re-runs Stimulus lifecycle callbacks. When the new markup lands, the poll controller's element is re-connected, and its connect() immediately re-applies this browser's state from localStorage:

So the division of labor is clean: the server owns the shared truth (counts, percentages, ordering), and the client owns its private state (which option I picked, whether my buttons are locked). After every morph, the server's truth is painted first, then connect() re-layers this browser's private state on top. localStorage is keyed per poll — ballot-poll-${this.idValue} — so it persists across morphs, across navigations, and across full page reloads. The morph can run a hundred times and your "I voted" highlight comes right back each time.

The upvote controller is the same pattern, smaller:

Bump the count optimistically, lock the button, persist to localStorage, POST. The server's UpvotesController mirrors the votes controller exactly — question.increment!(:upvotes_count), room.touch, head :no_content — and the morph reconciles. After the morph, connect() re-locks the button so you can't upvote the same question twice in this browser.

Charts with no charting library

There is no D3, no Chart.js, no canvas, no SVG-plotting dependency. A bar is a <div> whose width is a percentage. That's the whole chart.

The percentage is computed server-side by Option#share, and rendered straight into style="width: …%" with a CSS transition-[width]. This is what makes the morph so cheap and so smooth: when the authoritative tallies arrive, the only thing that changed in the markup is a number inside style="width:". Morphing patches that attribute in place, the CSS transition animates the new width, and the bar slides to its new length. No re-instantiation, no chart re-render, no layout thrash. The bar is the data.

The counter columns earn their keep here too. votes_count on options and upvotes_count on questions are plain integer columns, bumped with increment! — a single UPDATE … SET votes_count = votes_count + 1. No COUNT(*) over a votes table on every render, and the Q&A ordering (order(upvotes_count: :desc)) is an indexed column sort. The data model is built for the read pattern.

Questions: post one, the room re-sorts for everyone

Asking a question follows the same broadcast-as-truth philosophy, with one twist for the asker's own form. The controller creates the question and responds two ways:

The only thing the turbo-stream response does is replace the new_question frame with a fresh, empty form — so the asker's textarea clears and they can immediately ask another. The new question itself is not in that response. It doesn't need to be: create! saved a record that belongs_to :room, touch: true, so the room is touched, broadcasts_refreshes fires, and the morph adds the new question to the list — already inserted in the correct position by upvote order — on every screen, the asker's included.

Why these are good architectural choices

  • Model-as-broadcast-source via touch. Liveness is declared once, on the room, with broadcasts_refreshes. Every write path — votes, upvotes, new questions — reaches it through ordinary belongs_to … touch: true chains. There is no broadcast call scattered across controllers to keep in sync. Add a new kind of activity tomorrow and as long as it touches the room, it's live for free.
  • Counter columns over aggregate queries. votes_count and upvotes_count make both the write (atomic increment!) and the read (no COUNT, indexed sort) cheap. The percentage math is a tiny pure method, not a query.
  • Thin endpoints with a 204 contract. The write controllers do one thing and render nothing. UI is never produced by the request handler, only by the page template — so there's a single rendering path and no risk of the POST response and the broadcast disagreeing.
  • No charting dependency. The "chart" is a div width and a CSS transition. Nothing to bundle, nothing to keep up to date, nothing that breaks under morph. The visualization rides the exact same morph mechanism as everything else.
  • App-under-namespace structure. Ballot is fully self-contained — its own controllers, models (ballot_* tables), and views — yet it shares the showcase's themeable shell, which re-skins the chrome by overriding one CSS custom property with the app's amber accent. Six apps, one Rails codebase, no collisions.

What this unlocks for a product

Strip away the demo framing and Ballot is a reference implementation for a whole category of features clients ask for: live audience interaction. Conference and webinar polling. All-hands Q&A with upvoting. Live reaction tallies and sentiment bars during a stream. Leaderboards that re-rank as scores land. Product-feedback boards where the most-wanted item floats up. In each case the requirement is identical: it has to feel instant for the person acting, and it has to be correct and consistent for the room watching.

The pattern here delivers exactly that, and the maintainability story is the real selling point. The entire feature is two small Stimulus controllers (about 60 and 30 lines), four thin models, four thin controllers, and a handful of ERB partials. There is no client-side state library, no charting dependency, no WebSocket plumbing to hand-maintain, no SPA build pipeline. A Rails engineer can read the whole thing in fifteen minutes and extend it confidently — because the rules are simple: writes touch the room, the room broadcasts, the page morphs, and each browser re-applies its own state on connect. That is a codebase a team can own, not one that owns the team.

Honest trade-offs and production hardening

This is a portfolio demo, and we'd be doing you a disservice to pretend the demo's shortcuts are production-ready. They're the right shortcuts for a demo, and here's exactly what you'd change for a real deployment:

  • Vote integrity is client-trust only. "Vote once" is enforced entirely in localStorage in the user's browser. The server happily accepts every POST and increments the counter — there is no server-side dedup. Clearing storage, opening an incognito window, or simply calling the endpoint directly votes again. A real app needs server-side identity and deduplication: a per-user (or per-session/per-ballot) vote record with a unique constraint, so the count reflects distinct voters, not distinct clicks.
  • No authentication or authorization. Anyone who can reach a room can vote and post. Production wants real auth, plus room-level permissions (who can create polls, who can moderate Q&A, whether the room is open).
  • No rate limiting or abuse controls. The increment endpoints are wide open. A real deployment needs rate limiting, and Q&A needs moderation — length limits beyond required, profanity/spam handling, and the ability to hide or remove a question.
  • Optimistic divergence is masked, not resolved. The morph papers over optimistic drift by always reasserting the server's numbers — which is the right behavior — but there's no explicit handling of a failed POST. If the network request errors, the optimistic bump stays on screen until the next broadcast happens to correct it. Production would surface and roll back failures deliberately.

None of these undercut the pattern — they're orthogonal to it. The optimistic-UI-plus-authoritative-morph loop is exactly how you'd build the production feature too; you'd just bolt real identity, auth, and rate limiting onto the same skeleton. The demo isolates the interaction model so you can see it clearly, then tells you honestly where the guardrails go.

That's Ballot. A live, multiplayer, animated polling and Q&A surface — instant for the actor, correct for the crowd — built on Rails' own broadcast machinery and roughly ninety lines of Stimulus. The hard part of realtime UI was never the WebSocket; it was keeping perceived speed and shared correctness from fighting each other. Optimism plus morph is how you get both.
