Cadence

Realtime team chat with presence — built on the Rails monolith, no separate websocket service.

broadcast_append_to Action Cable presence typing indicator optimistic reactions

Cadence is one app inside a six-app Hotwire showcase. It is a realtime team chat: channels with a live message feed, a presence roster that fills in as people arrive, "X is typing…" indicators, and optimistic emoji reactions. What makes it worth a write-up is not the feature list — it is that the same screen runs two different realtime transports at once, and the choice of which to use where is the whole lesson.

Persistent content — the messages themselves — travels as HTML over the wire via Turbo Streams. Ephemeral signals — who is online, who is typing — travel as raw Action Cable JSON, because there is nothing to persist and nothing to render server-side. Both ride the same Action Cable connection, backed by Solid Cable on SQLite. No Redis, no Node websocket tier, no client framework. This post walks the code that makes that work.

01The shape of a channel

A request to /channels/:slug resolves a Channel, loads the last fifty messages with their authors, and the full member list. The controller is deliberately small — all the realtime behavior lives in the model and the view, not here.

The view opens a single Action Cable stream for the channel and renders the seeded messages into a list. One line — turbo_stream_from @channel — is the entire client-side subscription for new messages; turbo-rails handles the websocket plumbing.

That one <section> hosts three Stimulus controllers — chat, presence, typing — and threads the channel slug and the current member's name down to them as values. Three controllers, three concerns, no coupling between them.

02Two realtime patterns, chosen on purpose

The view's own caption states the thesis plainly: "Messages append via broadcast_append_to; reactions broadcast_replace just one message; presence + typing ride raw Action Cable channels — not DOM over the wire." Here is why each branch is what it is.

(a) DOM over the wire — the message feed

A Message is its own broadcaster. When one is created and the transaction commits, the model appends its rendered partial to the messages list for every subscriber. When one is updated — which only happens on a reaction — it replaces just that message, surgically, targeting its dom_id.

This is the crux of the "HTML over the wire" idea. The server renders the same partial it would render on a full page load, wraps it in a <turbo-stream> element, and ships it down the channel. The browser does no templating — Turbo finds the target element by ID and either appends or replaces. The append and the replace differ only in targeting: a new message goes onto the end of the list (target: "messages"), while a reaction surgically swaps the one element that changed (target: dom_id(self)). A full-feed refresh would be wasteful for a one-emoji change, and re-appending would duplicate the message. Targeting the dom_id is what keeps it surgical.

Because the model does the broadcasting, the controllers stay almost empty. MessagesController#create saves the message — the after_create_commit hook fans it out to everyone — and the controller's only job is to reset the composer for the sender who submitted it.

Note the division of labor: the broadcast handles every other browser, and the direct turbo-stream response handles only the sender's composer. The sender sees their message arrive through the same broadcast everyone else does — there is no special-cased local echo to keep in sync.

(b) Raw cable JSON — presence and typing

Presence and typing never persist anything and never need server-rendered HTML. Pushing a roster or a typing flag as a Turbo Stream would mean rendering a partial for a value that lives for seconds. So these two ride raw Action Cable channels that broadcast plain JSON, and the client decides what to do with it.

The rule that falls out of this: persistent content → HTML streams you can morph and re-render; transient signals → raw cable JSON the client renders ephemerally. Same connection, same Solid Cable backend — two transports chosen by the nature of the data.

03Presence: a cache-backed roster with heartbeats

Presence is "who is in this room right now." Cadence holds it in Rails.cache as a hash of name => last-seen-epoch, keyed per channel. There is no presence table — it is ephemeral by design, with a five-minute cache expiry and a two-minute liveness cutoff.

Every write prunes anyone whose last heartbeat is older than two minutes, so a roster naturally sheds stale entries even if an unsubscribed callback never fires — the common failure mode when a laptop lid closes or a tab is killed without a clean disconnect. The subscribe/unsubscribe lifecycle handles the happy path: arriving marks you present and broadcasts; leaving marks you absent and broadcasts again.

The client keeps itself alive with a heartbeat. The Stimulus controller subscribes on connect, performs present every thirty seconds, and — importantly — fires an extra heartbeat whenever the tab becomes visible again, so coming back from a background tab re-asserts your presence immediately rather than waiting out the next interval.

The disconnect() half matters as much as connect(): it clears the interval, drops the visibility listener, and unsubscribes the channel. Leaking a subscription or an interval across Turbo navigations is the classic Hotwire bug, and the symmetry here is what prevents it. When a roster arrives, the controller renders avatar initials straight from the JSON names — no server round-trip, because the data is trivially renderable on the client.

04Typing: throttled, self-silencing, self-expiring

The typing indicator is a study in restraint — three separate guards keep it from being annoying or chatty. First, start events are throttled: the controller sends exactly one start per typing burst and resets a 3-second timer on every keystroke, so the network sees one event, not one per character. Second, it auto-stops after a pause — when the timer elapses, or when the input goes empty, it sends stop.

Third — and this is the robustness move — there is a client-side purge. A 1-second interval sweeps the local typers map and drops anyone whose last start is more than five seconds old. So even if a stop event is dropped or a sender vanishes mid-keystroke, the indicator self-heals instead of hanging forever on "Jordan is typing…". And the very first line of received() drops any event bearing your own name, so you never see yourself typing — the indicator only ever reports other people.

05Optimistic reactions, reconciled by broadcast

Reactions are where the two halves meet. The interaction is optimistic: clicking an emoji bumps the visible count immediately, with no wait for the server, then fires the request in the background.

The server's job is to make that optimistic bump true for everyone. The reactions endpoint is a thin 204 — it persists the reaction and returns no body, because the actual UI update arrives over the broadcast channel, not in the HTTP response.

Reactions are stored as a small JSON counts hash on the message, and add_reaction guards against anything outside the fixed emoji set before incrementing. The update fires the model's after_update_commit, which broadcast_replace_tos the one message to the whole channel — so the clicker's optimistic +1 is confirmed and every other client receives the authoritative new count via a surgical replace of that single message element. The optimistic update makes the clicker's own UI feel instant; the broadcast makes it correct for the room.

One subtlety the replace creates: when the message element is swapped out from under you, the feed could jump. That is what the chat controller is for. It pins the scroll position to the bottom and re-pins on any DOM mutation in the feed — a new appended message, a replaced one, anything.

A MutationObserver is the right tool precisely because the feed is mutated by Turbo Stream broadcasts that the controller never sees directly — it does not know when an append or replace lands, only that the DOM changed. Observing mutations decouples "keep me scrolled to the bottom" from the transport entirely.

06One identity across HTTP and WebSocket

Chat needs to attribute messages and presence to a person, and that identity has to be the same whether a request arrives over HTTP or over the Action Cable socket. Cadence solves this with a shared encrypted cookie. On the HTTP side, the application controller resolves a stable member for the browser and writes their id and name into encrypted, permanent cookies.

The cable connection reads the same encrypted cookie to identify itself. identified_by :member_name makes that name available to every channel — which is exactly what PresenceChannel and TypingChannel use to label rosters and typing events.

Because both sides decrypt the same cookie, there is no separate token exchange, no auth handshake bolted onto the socket. The browser proves who it is once, via a cookie the framework already manages, and both transports trust it. In a real product this is exactly where your existing session/auth would plug in — the pattern is identical, you would just identify the connection by a real user.

07Why this matters for a product team

The reason to care about Cadence is not chat specifically — it is the class of features it stands in for. Live message feeds, threaded comments, presence rosters, "someone is typing," activity tickers, notification badges, live dashboards: every one of these is realtime collaboration, and every one of them is built here with the same two primitives.

No extra tier

It's the same Rails app

Realtime ships on the monolith. No standalone Node websocket service to deploy, scale, secure, and keep in sync with your data model. Action Cable + Turbo, backed by Solid Cable, on the box you already run.

No SPA tax

No heavy frontend framework

The server renders the same partials it always has. There is no client-side view layer to duplicate your templates in, and no JSON API to version. Stimulus controllers stay small and single-purpose.

Hiring & ownership

Any Rails dev can own it

A broadcast is a model callback. A roster is a cache hash. The whole realtime surface is readable Ruby and a handful of Stimulus files — not a separate codebase needing a separate specialist to maintain.

Right tool, right job

Two transports, clear rules

HTML-over-the-wire for things you persist and re-render; raw cable JSON for transient signals. The decision is principled, not ad hoc, so the next feature slots into one of two known patterns.

For a team weighing whether realtime "needs" a websocket microservice and a React front end, Cadence is the counter-argument in working code: a small, maintainable Rails surface delivers the multiplayer feel users expect, and it stays inside the stack the rest of the application already lives in.

08Honest trade-offs & production hardening

This is a showcase app on a single box, and it is built that way on purpose. Shipping the same patterns into production means tightening several things — none of them surprising, all of them real:

  • Authentication. Identity here is a demo convenience: a stable member is picked for the browser, and an unauthenticated cable connection falls back to "Guest". A real deployment would reject unauthenticated connections in Connection#connect and identify by an actual authenticated user, with channel-level authorization so a subscriber can only stream channels they belong to.
  • Cable scaling. Solid Cable on SQLite is ideal for a single-box demo and zero external dependencies. Across multiple app servers you would move the cable adapter to a backend that fans out between processes — a Redis adapter, or Solid Cable pointed at a shared database — so a broadcast on one node reaches subscribers on another.
  • Presence at scale. A per-channel Rails.cache hash with read-modify-write on every heartbeat is fine for modest rooms but is a contention point under load, and last-write-wins can race. High-traffic presence wants atomic per-member keys (or a Redis set with TTLs) rather than rewriting one shared hash.
  • Rate limiting. The reaction and message endpoints do no throttling, and typing/presence heartbeats are client-driven. Production would rate-limit message creation and reaction spam, and cap how often a client can heartbeat, to keep a single tab from flooding the channel.
  • Message volume. The feed loads the last fifty messages and appends forever. A real channel needs pagination / lazy history loading and a ceiling on the live DOM so long-lived tabs don't grow unbounded.

None of these change the architecture — they harden it. The two-transport split, the model-as-broadcaster, the shared-cookie identity, the optimistic-then-reconciled reaction: those patterns are exactly what you would keep. That is the point of a portfolio piece — to show the bones you would build a production system on, and to be honest about the muscle you would add.
