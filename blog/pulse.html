Pulse: a live ops dashboard with no polling and no charting JS

A monitoring board where background jobs are the broadcast source, charts are SVG paths the server draws, and the whole page reconciles itself by morphing. Built on Rails 8 + Turbo 8.

Active Job → Turbo Stream broadcasts_refreshes morph server-rendered SVG lazy Turbo Frames

Most "real-time dashboard" projects reach for the same shopping list: a polling loop on a timer, a WebSocket fan-out you hand-write, and a JavaScript charting library to draw the lines. Pulse does none of that. It is one of six self-contained Hotwire apps mounted inside a single Rails 8 codebase, and it exists to make one argument concretely: a live operations view — services with health, latency, error rate and throughput; sparklines that redraw as data lands; a deploy that streams its progress; incidents you acknowledge and resolve — is a server-rendered problem. The browser's only job is to morph the DOM.

This is a walk through how it actually works, file by file, with the real code. Everything below is in the repository; nothing is aspirational.

What Pulse is

The dashboard lives at /pulse and is registered in a small showcase manifest. Its identity — name, tagline, accent color, and the Hotwire primitives it demonstrates — is one row in app/lib/showcase.rb:

The themeable shell reads that accent pair and re-skins the chrome by overriding a single CSS custom property, so the entire indigo palette you see in Pulse is one variable. The data model is two tables. A Pulse::Service carries a status, the three headline metrics, a position, and a JSON column of recent latency samples. A Pulse::Incident belongs to a service (optionally), with a severity and a status drawn from a fixed set:

The dashboard controller is deliberately thin. It loads services by position, orders incidents so that resolved ones sink to the bottom, and excludes down services from the deploy picker:

That Arel.sql ordering is worth pausing on. status = 'resolved' evaluates to a boolean that SQLite sorts as 0 then 1, so open and acknowledged incidents float to the top and resolved ones settle below — then started_at DESC breaks ties. It is a single sort expression doing what would otherwise be a partition-and-concatenate in application code.

The signature pattern: a background job is the broadcast source

The most important idea in Pulse is that nothing on the client asks "is there anything new?" on a timer. The page subscribes to one stream and waits. New state arrives because a background Active Job pushed it. The deploy flow is the cleanest demonstration.

The view subscribes to a single named stream — defined as one constant on the module so every broadcaster and the view agree on the channel:

When you submit the deploy form, the controller does almost nothing. It enqueues a job, immediately replaces the progress widget with a 0% bar via Turbo Stream, and returns. The slow work happens off the request thread:

The job is where the pattern lives. It flips the service into a deploying state and broadcasts a refresh (more on that in a moment), then loops over a fixed set of progress percentages, broadcasting a replace of the small progress partial at each step. When it finishes, it flips the service back to healthy with an improved latency, broadcasts a "done" progress frame, and broadcasts a final refresh so the whole board reconciles:

Notice the two broadcast styles working together. The progress bar is a surgical replace — only the deploy_status fragment changes, eight times, so a targeted broadcast_replace_to is exactly right. But the status pill on the service card, the aggregate tiles at the top, the avg-latency math — all of that should change when a service goes from deploying back to healthy. Rather than hand-target each of those fragments, the job broadcasts a single refresh and lets the morph reconcile the entire page. One line covers everything the deploy touched that isn't the progress bar.

The progress partial itself is a small state machine over those locals — active shows a bar, done shows a checkmark, neither shows the idle prompt:

The width animation is plain CSS (transition-[width]); the server just keeps shipping new percentages. Open the dashboard in two browser tabs, run a deploy in one, and the bar fills in both — because both are subscribed to Pulse::STREAM and the broadcast goes to every subscriber.

The same shape powers Pulse::SampleJob, the "Simulate traffic" button. It jitters each non-down service's metrics over a few ticks, recomputes its status from thresholds, pushes a new latency sample onto the rolling window, and broadcasts a refresh after each tick:

Each tick mutates real rows and broadcasts a refresh, so every connected dashboard morphs its sparklines, status pills, and aggregate tiles in lockstep — six times, half a second apart. The trigger endpoint is a textbook thin controller action: enqueue and return 204 No Content.

The job owns the truth. The controller only kicks it off; the stream carries the result. No timer ever runs in the browser.

Server-rendered SVG sparklines

There is no charting library anywhere in Pulse — no Chart.js, no D3, no canvas. The latency history for each service is a JSON array stored on the row, and the chart is an SVG path the server computes in a helper. Samples are kept as a rolling window directly on the model:

Twenty-four points, oldest dropped as new ones arrive. The SampleJob calls push_sample(service.latency_ms) every tick, so the series is always the most recent two-dozen readings. Turning that array into a chart is the entire contents of PulseHelper:

The math is a min/max normalization. Each value maps to a y between the padded top and bottom of the box; the x steps evenly across the width. The SVG y axis grows downward, which is why the formula subtracts the normalized height from (height - pad) — higher latency draws higher on the card. It returns two strings: line is the polyline points, and area is the same points wrapped down to the baseline at both ends so it closes into a filled polygon. The service partial renders them directly:

The fill is var(--color-accent-soft) and the stroke is var(--color-accent) — the same theme variables the shell sets per app, so the sparkline is automatically indigo in Pulse without a single hard-coded color. The sparkline at the very top of this page is exactly this output shape: a closed polygon under a polyline. Because the SVG is part of the server-rendered page, when a refresh broadcast lands and the DOM morphs, the points attributes change in place and the line simply redraws. There is no chart instance to update, no .render() call, nothing to tear down — the morph is the chart update.

Morphing dashboards

The reason a whole-page refresh broadcast doesn't feel like a reload is Turbo 8 morphing. The layout opts every navigation and refresh into morph semantics with three meta tags:

When broadcast_refresh_to fires, each subscribed browser re-fetches the current page and reconciles its existing DOM against the new HTML using idiomorph rather than swapping the body wholesale. Nodes that didn't change are left alone; scroll position and focus are preserved. If you're hovering an Acknowledge button or mid-scroll down the incident list when a sample tick lands, you stay exactly where you were while the sparklines and metric numbers update underneath you. On browsers that support the View Transitions API, the change is wrapped in a same-origin transition for a soft cross-fade; everywhere else it degrades silently.

Incidents participate in the same morph. Acknowledging or resolving one is a thin update that broadcasts a refresh and returns 204 — the validation against the fixed status set lives right in the action:

Resolve an incident and the refresh re-renders the board; the Arel ordering from the controller re-sorts it to the bottom of the list, where the partial renders it dimmed and struck through. The state transition, the re-sort, and the visual treatment all flow from one broadcast.

Lazy panels

The "Recent events" feed at the bottom of the dashboard doesn't load with the page. It's a deferred Turbo Frame with a src and loading: :lazy, so the browser only requests it when it scrolls into view, showing a placeholder until then:

The frame resolves to a generic panel route — get "panels/:panel", to: "dashboard#panel" — which renders the requested partial. The events panel derives a recent-activity feed straight from the services' updated_at timestamps, so it reflects the same data the sparklines do, formatted as a log:

Deferring the panel keeps the initial render lean — the expensive or below-the-fold piece is a separate request the page makes on its own, with no JavaScript to wire it up.

Why these choices are good ones

A few decisions compound into something maintainable:

  • Jobs as the single broadcast source. State changes and the broadcasts announcing them live together in the job. There's no scatter of broadcast calls across callbacks, controllers, and views to keep in sync — if you want to know what makes the board move, you read three job files.
  • One STREAM constant. The channel name is defined once on the module. The view subscribes to it, every broadcaster targets it. Rename it in one place and nothing drifts.
  • Thin endpoints. simulate and incidents#update return 204 No Content; deploys#create enqueues and replaces one fragment. The HTTP request is never holding the connection open while work happens — the stream delivers the result asynchronously.
  • The server owns rendering, including charts. Sparklines are an ERB helper and an SVG element. There is no client charting dependency to version, audit, or theme. The chart inherits the page's CSS variables for free and updates by morph.
  • Idempotent, plausible seed data. Pulse.seed! returns early if any service exists, and seeds each one with a synthesized latency series so the sparklines look alive on first load:

The jitter helper layers a sine wave and a small sawtooth over a baseline to produce 24 sample points that read as real telemetry — never below 1 — without any external data.

Why this matters for the work we do

Pulse is a portfolio piece, but the pattern is the product. The "background job streams progress to the page over a named stream, and a refresh morphs the rest of the view" shape is the exact thing most business software needs and usually over-builds:

  • Admin panels and internal dashboards that must reflect live state — orders, queue depth, fleet health — without every analyst's browser hammering an endpoint on a timer.
  • Long-running work surfaced to users live: a CSV import, a report generation, a deploy, a batch reconciliation. The deploy progress bar in Pulse is a literal template for "show the user a job filling up" — enqueue, stream percentages, finish with a refresh.
  • Real-time monitoring views where the metrics and their charts are owned by the server, so there's no front-end charting stack to staff, secure, or keep on a release cadence.

The hiring argument is the maintainability one. There is no separate front-end application here — no build step beyond importmap and a Tailwind gem, no chart library, no client state store, no polling logic to debug. A Rails engineer can read the whole feature: two models, three controllers, two jobs, one helper, a handful of partials. That is a smaller surface to own, a shorter path from "we need a live view of X" to shipping it, and one fewer specialty to hire for.

Honest trade-offs and production hardening

The job sleeps, and a sleeping job holds a worker

Both jobs use sleep between broadcasts (sleep 0.45 in the deploy, sleep 0.6 per tick in the sampler). That's perfect for a demo — it paces the animation visibly — but a sleeping job occupies a Solid Queue worker for its whole duration. In production you would not pad real work with sleeps; progress would be broadcast as actual stages complete, and a slow multi-minute job would be designed so it doesn't starve the worker pool (more workers, a dedicated queue, or breaking the work into enqueued stages).

The metrics are simulated

The numbers come from jitter and from rand in SampleJob; there is no real telemetry ingestion. A production Pulse would feed push_sample from an actual metrics source — a periodic collector, a webhook, or a stream consumer — but the rendering and broadcast path downstream of push_sample would not change at all. That's the point: the display layer is already production-shaped.

No authentication or authorization

The dashboard is open, and the deploy/simulate/incident actions are unauthenticated by design for a public demo. Anything resembling this in production needs access control on the mutating endpoints and likely per-tenant scoping of the stream so one customer's broadcasts don't reach another's subscribers.

Sparkline fidelity is intentionally coarse

The chart is a 24-point min/max-normalized polyline with no axes, gridlines, or tooltips. That's appropriate for an at-a-glance trend indicator and nothing more. If a view needs precise reads, hover values, or a fixed scale across services, the SVG approach still holds — you'd extend the helper — but you'd be writing that yourself rather than getting it from a charting library.

Solid Queue and Solid Cable on one SQLite box

The whole stack — jobs, Action Cable, cache — runs on SQLite with the Solid adapters and no external services. That's a genuine strength for a single-box deploy and a real simplification. At higher broadcast volume or across multiple app servers you would reassess the Cable backend and queue throughput; the abstractions (Active Job, Action Cable) stay the same, so it's a configuration change, not a rewrite.

None of these are surprises hiding in the code — they're the expected boundary between a faithful demo and a hardened system, and the architecture is built so that crossing that boundary is mostly swapping the data source and adding policy, not redrawing the design.

Pulse makes a narrow, sharp claim: the live dashboard you were about to build with a polling loop and a charting library is a Rails problem. Enqueue a job, broadcast over one stream, render the chart as SVG, and let the page morph. The result is fewer moving parts, one language to maintain, and a feature any Rails engineer can pick up and extend.
