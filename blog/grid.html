A spreadsheet with live formulas — and no formula engine on the client

Editable cells, a derived Total column, and a grand total that stays correct across every open tab. All the arithmetic lives in Ruby. The browser ships no spreadsheet library and no SPA grid.

What Grid is

Grid is one of six self-contained Hotwire apps mounted inside a single Rails 8 codebase. It is a spreadsheet-lite — Airtable shrunk to the part that matters for most line-of-business work: a sheet of rows, with cells you click to edit, and a couple of columns that are computed, not typed.

A sheet (Grid::Sheet) has many rows (Grid::Row). Each row carries four editable fields — label, category, qty, and unit_price — plus two values that are never stored anywhere: the row's Total (qty × unit_price) and the sheet's grand_total (the sum of every row total). The seed data ships two sheets, a "Q3 Cloud Budget" and a "Launch Forecast," so the demo reads like a real budgeting tool rather than a toy.

The thing worth studying here is not the spreadsheet — it is the pattern that makes it feel live: frame-scoped cell editing, server-side formula recompute, and a morph broadcast that keeps the derived numbers honest for everyone looking at the sheet. Let me walk it precisely, because every piece is small and the whole is the point.

The signature pattern, step by step

Editing one cell triggers a chain that is deliberately short. Here is the entire controller that handles a cell edit:

That is the whole endpoint. It finds the row, hands the field name and value to the model, and returns 204 No Content. There is no render, no Turbo Stream template, no JSON. The response body is empty on purpose — the UI does not update from this response at all. It updates from a broadcast that the save itself triggers. Follow the thread into the model:

assign_cell does three things, in order, and each one is a guardrail:

  1. Allowlist. return unless EDITABLE.include?(field) — a request can only ever write one of four columns. There is no path to set id, sheet_id, position, or created_at through this endpoint, regardless of what the client sends.
  2. Coercion. For the two numeric fields, the incoming value is run through value.to_s.gsub(/[^\d]/, "").to_i — strip everything that isn't a digit, then cast to integer. A user can type $1,800 or 180/mo into a price cell and the server quietly distills it to 1800 or 180. Garbage in, integer out.
  3. Save. update(field => value) writes the single column and runs validations: label must be present, qty and unit_price must be non-negative.

The pivotal line is at the top: belongs_to :sheet, touch: true. When the row saves, ActiveRecord bumps the parent sheet's updated_at. And the sheet listens for exactly that:

broadcasts_refreshes is the Turbo 8 default broadcast. On every commit to the sheet record, it pushes a single <turbo-stream action="refresh"> down the Action Cable channel. Each subscribed browser reacts by re-fetching the current page and morphing the new HTML onto the existing DOM with idiomorph — preserving scroll position, focus, and any data-turbo-permanent nodes. Only the cells whose rendered text actually changed get touched in the DOM.

The sheet's show view subscribes with one line — <%= turbo_stream_from @sheet %> — and that is the entire realtime wiring. No channel class, no hand-written broadcast call, no stream template. The touch: true on the association does the plumbing.

Why 204 and not a rendered partial? Because the edit and the update are decoupled. The PATCH's job is to persist the new value. The job of showing the result belongs to the refresh broadcast — which fires for the editor's own tab too, since their browser is also subscribed to the sheet. One mechanism updates every client identically, including the one that made the change. Returning a partial would mean two code paths painting the same pixels, and they would eventually drift.

Formula cells are derived, never stored

This is the design decision the whole app is built to demonstrate. Look at where the totals come from. The row total is a method — def total = qty * unit_price. The grand total is a method — def grand_total = rows.sum(&:total). Neither is a database column. Neither is cached. Neither is sent by the client. They are computed in Ruby, on read, every time the page renders:

Because the formula cells are derived at render time, they cannot fall out of sync with the inputs. There is no "recalculate" step to forget, no stale cached aggregate, no invalidation logic, no client formula parser to keep consistent with the server's. Change a qty from 6 to 7 and the row total and the grand total are simply different the next time the page renders — and the morph broadcast guarantees that next render happens immediately, on every open tab. The server is the single source of truth for the arithmetic, and there is exactly one place that arithmetic is expressed.

That is the clean version of "live formulas." The alternative — store total as a column, recompute it in a callback, and ship a formula engine to the browser for optimism — is three moving parts that can disagree. Here there is one.

Frame-scoped cells: instant edit, server authoritative

Each cell renders the same partial. Reading it carefully shows how click-to-edit can be instant and keep the server in charge:

Every editable cell contains both its display and its edit form, pre-rendered, in the same node. The display is a <button>; the form sits right beside it with class hidden. Nothing is fetched to enter edit mode. The Stimulus controller just swaps which one is visible:

Click a cell and the form appears with zero latency — there is no round-trip to "enter edit mode," because that hop was always the source of the lag. The input is focused and the caret placed at the end. The number input carries onchange: "this.form.requestSubmit()", so committing a value (blur or Enter) auto-submits the PATCH. From there the server takes over: it saves, touches, and the refresh broadcast morphs the canonical display back into place — for this tab and every other.

So the JavaScript handles only one thing — the visual flip between display and input — and never owns the data. The instant feel is local; the truth is remote. The controller's own comment frames it exactly: "the server stays authoritative and other clients still morph."

Each cell is rendered into its own <td> with its own inline-edit controller instance and its own form scoped to that one row and field (hidden_field_tag :field tells the endpoint which column). An edit to one cell never disturbs another. The blast radius of a click is a single cell — and the blast radius of a save is precisely the formula cells that depend on it.

Input coercion and safety, in one place

It is worth restating the safety story because it is unusually tidy. Three lines in the model do all of it:

  • Column allowlist. EDITABLE = %w[label category qty unit_price] — the only writable surface. A crafted request setting row[sheet_id] or row[position] is dropped on the floor by the return unless EDITABLE.include?(field) guard. This is mass-assignment protection expressed as data, not as a strong-params incantation buried in a controller.
  • Numeric sanitization. value.to_s.gsub(/[^\d]/, "").to_i means the numeric columns can only ever receive a non-negative integer, no matter what arrives. Currency symbols, commas, stray letters — all stripped before the value reaches the database.
  • Validations. label presence and non-negative numericality on qty/unit_price back-stop it at the persistence layer.

The endpoint itself is two lines of logic. All the rules live in the model, where they are unit-testable in isolation and impossible to bypass by hitting the route differently.

Why these choices are good engineering

  • One source of truth for every number. The formulas are Ruby methods, evaluated at render. No client formula engine to ship, version, or keep in lockstep with the server. No derived columns to invalidate.
  • Consistency for free, for everyone. broadcasts_refreshes + morph means the grand total is correct on every connected tab the instant any input changes — and the editor's own tab updates through the same broadcast as everyone else's, so there is no "did the optimistic update match the server?" reconciliation bug class.
  • Thin endpoints. The cells controller is five lines. The sheets controller is index / show / reset. The realtime layer is one association option (touch: true) and one model macro (broadcasts_refreshes). There is very little surface area to break.
  • Namespaced, self-contained models. Everything lives under Grid:: with a grid_ table prefix (def self.table_name_prefix = "grid_"), so this app's schema never collides with the five other apps sharing the codebase. You can lift Grid out, or reason about it in isolation, without spelunking the rest.
  • Progressive enhancement by construction. Display and form are both real HTML, the form is a real <form> PATCH, the route is a real URL. Stimulus only makes the swap instant.

Why this matters for clients

The "editable data grid with live rollups" is one of the most-requested and most-over-engineered surfaces in line-of-business software. Budgets. Pricing tables. Quote builders. Inventory sheets. Admin CRUD with running totals. Forecast models. The default reflex is to reach for a heavyweight client-side grid component or a full SPA, ship a JavaScript formula engine, and then spend the rest of the project chasing sync bugs between the optimistic client and the authoritative server.

Grid shows the Hotwire alternative is not a compromise:

  • Collaborative and instant — multiple people edit the same sheet and everyone sees correct totals immediately, with no manual broadcast code.
  • No SPA grid library — the entire front end is a Rails table partial, one tiny Stimulus controller, and importmap (no Node build step at all).
  • Formulas owned by the server — which means they are auditable and testable. A row total is a Ruby method you can assert on in a unit test; you cannot ship a wrong number to one client and a right number to another, because there is only one implementation.
  • Maintainable by the team you already have. A Rails engineer who has never touched this code can read the five-line controller, the three-line assign_cell, and the two model macros and understand the whole feature in a few minutes. That is the hiring and handoff argument: less novel client architecture means lower onboarding cost and fewer ways for the next person to introduce a regression.

For most internal tools, that is the right trade every time. You get the collaborative, instant feel users associate with expensive SPA grids, with a fraction of the moving parts and a codebase your whole Rails team can own.

Honest trade-offs & production hardening

This is a focused demo, and it is honest about its scope. To take this pattern to a production system, here is what genuinely needs work:

  • Real formula dependency graphs. The formulas here are a fixed shape: total = qty × price, grand total = Σ totals. A real spreadsheet lets cells reference arbitrary other cells, which means a dependency DAG, cycle detection, and topological recompute. That is a substantially larger model than two Ruby methods — Grid deliberately demonstrates the delivery pattern (derive on the server, morph to clients), not a general formula language.
  • Large-sheet performance. Every edit triggers a full-page re-fetch and morph. Idiomorph only touches changed nodes, so the DOM cost is bounded, but the server still re-renders the whole table and grand_total re-sums every row on each edit. For thousands of rows you would paginate or windowing the table, scope the broadcast to a fragment, and consider a cached aggregate with careful invalidation.
  • Optimistic concurrency. Two people editing the same cell at the same time is last-write-wins today. A production version would add a lock version (ActiveRecord's lock_version) or per-cell conflict detection so simultaneous edits surface a conflict instead of silently clobbering.
  • Authentication and authorization. The showcase uses a demo identity and a "Reset sheet" escape hatch (Grid.seed!) so visitors can't permanently wreck the shared state. A real deployment needs real auth, per-sheet authorization, and scoped broadcasts so users only receive updates for sheets they may see.

None of these undercut the core lesson. They are exactly the line items you would scope in a kickoff — and the architecture here gives you a clean, well-bounded place to add each one, because the data, the formulas, and the realtime delivery are already cleanly separated.
