Workspace: a Jira-grade delivery board, built on Hotwire

SPA-grade interactivity — drag-and-drop, live multiplayer sync, command palette, inline editing — with server-rendered HTML and remarkably little JavaScript.

SortableJS drag broadcasts_refreshes morph Turbo Frame drawer instant inline edit

Workspace is one app inside a Rails 8 Hotwire showcase — a team delivery board in the spirit of Linear, Jira, or Basecamp. You drag a card between columns and every other open browser re-settles to match. You click a card and a detail drawer lazy-loads; you edit a field in place with zero perceptible latency; comments stream in live. There is a debounced search frame, a ⌘K palette, an infinite-scroll activity feed, and a sign-up form that validates field-by-field against the server.

What makes it worth writing up is not the feature list — it's that almost none of it is hand-written client state. The interactivity comes from a small number of Hotwire primitives composed carefully. This post walks the real code, file by file, and explains the engineering decisions behind each one.

01 / DATA MODELWhat the app actually is

The domain is small and conventional. A Project has ordered Columns; each column has ordered Issues; issues have Comments and an optional Member assignee. That's the whole spine of the board.

Two details here pay off across the whole app. First, broadcasts_refreshes — the single line that makes the board multiplayer (more on it in section 02). Second, next_issue_number wraps a database row lock around a counter so that issue keys (LB-14, MOB-3) are allocated atomically. The sequence lives on the project (issues_seq) rather than being derived from COUNT(*), so deleting an issue never recycles a key — exactly how you'd want a real tracker to behave.

The board's "live" behaviour is wired by ordinary association options, not callbacks:

Because Issue belongs_to :column, touch: true and Column belongs_to :project, touch: true, any write to an issue bubbles a touch up to its project. The project's broadcasts_refreshes turns that touch into a broadcast. There is zero hand-written broadcast code on the move path — the association graph does it.

02 / THE SIGNATURE PATTERNDrag → PUT → morph everywhere

This is the demo's centerpiece, and the part that most cleanly separates "knows Hotwire" from "has read about Hotwire." Drag a card in one window; it moves in every connected window. Here is the entire client side:

SortableJS owns the drag interaction and mutates the DOM directly. On drop, the controller reads three values straight off the dropped node (data-position-url, the destination column's data-column-id, and SortableJS's computed newIndex) and fires a single PUT via @rails/request.js — which transparently includes the CSRF token. That's the whole client contribution: no optimistic store, no diffing, no rollback logic.

The server endpoint is deliberately thin. It moves the issue, renumbers the destination column to match what the user just did, and returns 204 No Content:

The reorder logic is small but careful. It pulls the destination column's other issues in order, clamps the drop index into 0..size (the comment is explicit about why: Array#insert past the end pads with nils), inserts the moved card, and rewrites positions — but only for rows whose position actually changed (if issue.position != index), avoiding redundant writes. Everything runs in a transaction, so a half-applied reorder can't be observed.

Now the magic step. The endpoint returns 204 and writes no HTML. So how does every browser update? Each board view subscribes to the project's refresh stream:

The transaction commits → the touch chain fires → broadcasts_refreshes emits one <turbo-stream action="refresh"> to every subscriber. Each browser then re-requests the current page and morphs the DOM into the new HTML using idiomorph, rather than replacing it. The layout opts the whole app into this:

Why this is correct, not just clever

The subtle reason this works: the drag state lives in the DOM. SortableJS has already moved the node by the time the morph arrives. Morphing reconciles the existing tree toward the server's HTML — so for the browser that did the drag, the incoming HTML already matches what's on screen, and the morph is a no-op on those nodes. There is no "snap back" from the server, no fighting between an optimistic update and an authoritative one. The other browsers, whose DOM doesn't match yet, get exactly the moved cards reconciled in place while their scroll position and focus are preserved. One broadcast, every client converges, and the client that initiated never sees a flicker.

03 / THE ISSUE DRAWERA lazy Turbo Frame <dialog>

Clicking a card opens a detail drawer. The card is just a link that targets a named frame:

One element carries three behaviours at once: it's the SortableJS drag handle (data-position-url is the PUT target), it's a navigable link, and data-turbo-frame="modal" routes its response into the persistent modal frame defined once in the layout:

The frame starts empty. When a card is clicked, Turbo fetches issues#show and splices the response into #modal; the resulting turbo:frame-load event triggers modal#opened, which calls the native <dialog>.showModal() — giving us a real top-layer modal with a backdrop, focus trapping, and ESC handling for free. On close the controller clears the frame so the next card always loads fresh. The wrapper is data-turbo-permanent, so the dialog element itself survives Turbo navigations and isn't re-created on every board morph.

Inline frame-swap field editing

Inside the drawer, each editable attribute is its own Turbo Frame with its own tiny edit lifecycle. The controller enforces a strict allowlist:

The permitted_field guard is the load-bearing security detail: the field name is interpolated into a partial path (issues/fields/#{@field}), so it must be validated against a fixed allowlist before it reaches the renderer — otherwise it's a path-traversal footgun. The code raises a routing error on anything not in FIELDS. Changing the status remaps the issue to the chosen column and appends it (position: target.issues.count); the assignee path normalises a blank selection to nil; everything else is a plain attribute update. Each branch re-renders just that field's display partial — and because the update touched the issue, the board still morphs for everyone else.

Streamed comments

Comments stream in without the controller knowing anything about who's watching. The model does the broadcast:

The open drawer subscribes with <%= turbo_stream_from @issue %> and renders a container at dom_id(@issue, :comments). When anyone posts, the after-commit callback appends the new comment to that target for every viewer of the issue. The controller, meanwhile, only resets the composer for the submitter — it relies entirely on the broadcast for the actual append. This is the deliberate counterpoint to the board: a single small fragment is being added, so a surgical broadcast_append_to is the right tool, where the board's wholesale reorder calls for a morphing refresh.

04 / ZERO-LATENCY INLINE EDITBoth states, rendered up front

Some fields (title, description) use a sharper trick than a frame round-trip. The display markup and the edit form are both rendered into the frame on first paint; the form is just hidden. Entering edit mode is a class toggle — no server hop at all.

The clever part is that this is pure progressive enhancement. The display is a real link_to pointing at issue_field_path(issue, :title) — the same GET endpoint edit_field serves. With JavaScript disabled, clicking it navigates the frame to a server-rendered edit form; with JS, event.preventDefault() intercepts the click and reveals the already-present form instead. Either way, submission goes through the same PATCH to update_field, and the server returns the canonical display partial. The optimisation removes the perceived latency of entering edit mode while keeping the server as the single source of truth for the saved value.

05 / SUPPORTING PATTERNSSearch, palette, feed, validation

Debounced live search — with a shareable URL

The search page auto-submits a real GET form into a results frame as you type, advancing the URL so results are bookmarkable and survive the back button:

The debounce controller is nine lines — clearTimeout / setTimeout(() => this.element.requestSubmit(), delay). The query itself is a plain LIKE against title and description, capped at 40 rows. The same controller-rendered results partial is reused by an inline topbar combobox (combobox_controller.js) that drops a panel under the input instead of navigating — and that combobox also degrades to a normal full-page search when JS is off, because the wrapper is a genuine <form>.

⌘K command palette — server-ranked, no client index

The palette opens on ⌘K/Ctrl-K (bound declaratively in the markup with keydown.meta+k@window), debounces typing into a fetch, and the Stimulus controller handles arrow-key navigation and Enter-to-visit. Crucially, ranking happens on the server — build_commands assembles navigation targets, every project, every channel, and the 20 most-recently-updated issues, then filters by substring. There is no client-side index to build, stale, or ship. The client only manages selection state over server-rendered <a> elements.

Infinite scroll — with no scroll listener

Each rendered page ends in a lazy turbo_frame_tag whose src points at the next page. loading: :lazy means Turbo fetches it only when the frame scrolls into the viewport — and that next page renders its own trailing lazy frame, chaining indefinitely. The result is infinite scroll with no IntersectionObserver and no scroll handler in sight. The feed itself is a nice touch: Activity is a tableless Ruby object that assembles real records (issues, comments, messages) into a sortable stream, so the pagination demo runs over genuine data rather than fixtures.

Live form validation — one source of truth

Signup is an ActiveModel form object (not a table) carrying the real validations: subdomain format, reserved-word check, email regexp, seat bounds. On blur, the validate Stimulus controller posts the whole form plus the focused field name; the server runs the model's own validations and stream-replaces just that field's frame with the rendered errors. The headline benefit is written into the model's comment: "the validations here are the single source of truth — the client renders the very same model errors." No validation rule is duplicated in JavaScript, so the inline feedback and the final submit can never disagree.

06 / ARCHITECTUREWhy these choices are good engineering

  • Thin endpoints, fat HTML. The drag endpoint returns 204; comment creation returns only a reset composer; field edits return a single partial. The controllers don't assemble JSON payloads or worry about what's on screen elsewhere — that's the broadcast's job.
  • The model is the broadcast source of truth. broadcasts_refreshes on the project and after_create_commit on the comment mean real-time behaviour is a property of the data, not scattered through controllers. A new code path that touches an issue is automatically multiplayer.
  • Two realtime strategies, used deliberately. Wholesale board changes use morphing refresh; a single new comment uses surgical append. The app demonstrates that the choice is intentional, not dogmatic.
  • Concurrency handled where it matters. next_issue_number uses with_lock; reorders run in a transaction. The hot paths that two users can hit at once are the ones that take care.
  • A themeable shell from one CSS variable. The layout sets --color-accent per app and the chrome re-skins itself — six products share one shell, and adding an app is "one row in showcase.rb plus its controllers/views."
  • Minimal JavaScript, all of it small. Nine Stimulus controllers, none over ~80 lines, each doing exactly one job. There is no client router, no store, no build step for app code (importmap).

07 / FOR CLIENTSWhy this maps to real products

Strip away the demo framing and Workspace is the shape of a large class of real software: project trackers, CRMs, support inboxes, admin dashboards, internal ops tools. They all want the same things — drag-to-reorder, real-time collaboration, detail panes, inline editing, fast search, a command palette. The conventional answer is a React/Vue SPA with a separate JSON API, a client cache, optimistic-update plumbing, and a build pipeline to maintain.

This codebase delivers that UX with server-rendered HTML and a handful of tiny Stimulus controllers. The hiring and maintenance argument writes itself: a Rails engineer can read this entire app end to end in an afternoon, the validation rules live in exactly one place, and the real-time wiring is a property of the models rather than a distributed system you have to reason about. Fewer moving parts means fewer ways to break and a smaller surface to onboard the next developer onto.

08 / TRADE-OFFSWhat you'd add for production scale

An honest portfolio piece names its gaps. This is a public demo, and the code reflects that:

  • No authentication or authorization. Identity is a "pick a stable member from an encrypted cookie" convenience (ApplicationController#current_member); every visitor shares the seeded boards, with a "Reset board" button as the safety valve. A real deployment needs accounts, per-tenant scoping, and policy checks on the field-edit and position endpoints.
  • Boards render in full. projects#show loads every column and issue, and a morphing refresh re-renders the whole board. That's ideal for demo-sized boards; at thousands of cards you'd paginate or virtualize columns and likely switch the busy paths to targeted stream updates.
  • No write-conflict handling. Concurrent drags are serialized by the per-request transaction and reconciled by the next morph, but there's no optimistic-locking or last-writer-wins policy surfaced to users. A production tracker would want explicit conflict semantics.
  • Search is LIKE. Fine for the seeded dataset; a real corpus wants a proper index (Postgres full-text or an external engine) and relevance ranking.
  • Activity feed is recomputed. The tableless Activity assembles its stream on each request — perfect for a demo over real records, but a high-traffic feed would be materialized.

None of these are Hotwire limitations — they're the normal distance between a sharp demo and a multi-tenant product, and each has a well-trodden Rails answer. The point of the demo is that the interaction layer — the part teams usually reach for a SPA framework to build — is already here, server-rendered, and small.

The throughline: by keeping interaction state in the DOM and treating the model as the source of broadcast truth, Workspace gets multiplayer drag-and-drop, lazy drawers, instant inline editing, and live validation without a client-side state-management layer. That's the Hotwire thesis, and this app is the proof.
