Spindle: a player that keeps going as you browse

One data-turbo-permanent element, one long-lived Stimulus controller, and a Web Audio engine that never stops — across every navigation in a server-rendered Rails app.

data-turbo-permanent

Spindle is one of six self-contained Hotwire apps living in a single Rails 8 codebase. Its whole reason to exist is one deceptively hard behavior: press play on a track, then wander the app — switch albums, hit back, follow a link — and the music never cuts out, never restarts, never re-mounts. This is the kind of persistent UI that teams usually reach for a SPA framework to get. Spindle does it on server-rendered HTML with a single permanent DOM node and roughly 160 lines of Stimulus. Here is exactly how it works, straight from the code.

01 / WHAT IT ISAn album browser with a player that outlives the page

The Rails side of Spindle is intentionally boring — which is the point. It is two models and a read-only controller. Spindle::Album has_many :tracks, ordered by position. The controller does nothing exotic:

The library page renders a grid of album cards; an album page lists its tracks, each row carrying a play button. Routes are equally plain — a namespaced resources :albums, only: [:index, :show], param: :slug. There is no audio model, no has_one_attached, no streaming endpoint. The interesting part is entirely about what happens between these two pages: the player that sits at the bottom of the viewport has to survive the transition from /spindle/albums to /spindle/albums/night-shipping with its audio intact. That is the trick worth dissecting.

02 / THE SIGNATURE PATTERNOne permanent element in the layout

Turbo Drive replaces the page <body> on every navigation. With Turbo 8 the showcase opts into morphing rather than wholesale replacement — the layout declares it globally:

Morphing reconciles the new HTML against the existing DOM (via idiomorph) instead of throwing it away, which already preserves scroll and focus. But morphing alone is not enough to protect a live audio graph — a morph can still re-create the node, and an oscillator graph cannot be serialized and re-hydrated. That is where data-turbo-permanent earns its keep. An element marked permanent, with a stable id, is treated by Turbo as sacred: across both Drive navigations and morph refreshes, Turbo carries the exact same DOM node forward from the old page to the new one rather than rendering a fresh copy. The node is never detached and re-attached, so its attached Stimulus controller is never disconnected and re-connected, and any JavaScript state it holds — including a running AudioContext — keeps running.

The player is exactly that node:

Two constraints follow directly from how permanent elements work, and the code respects both. First, the node must live in the layout, not in a page template. A permanent element only persists if a node with the same id exists on the destination page too; if it lived inside albums/show.html.erb it would not exist on a non-Spindle page and Turbo would have nothing to preserve it against. Rendering it once in the layout means it is present on every page in the app, so Turbo always finds its twin and carries the original forward. Second, the layout renders it only for Spindle, gated on the current app:

current_app is inferred from the controller path in ApplicationController#assign_current_app — the spindle/ namespace resolves to the Spindle app entry in Showcase::APPS, which also supplies the #7c3aed violet accent the whole shell is re-skinned with. The player is therefore present on every page you can reach within Spindle, and only those, so navigating between the library and any album preserves the node while leaving the rest of the showcase unburdened by it.

03 / THE DECOUPLINGA track row and the player never touch directly

If the play button on a track row called into the player controller directly, that coupling would break the moment the page re-rendered — the row is part of the disposable page body, the player is not. Spindle sidesteps this entirely with an event bus. A track row's button is its own tiny Stimulus controller whose only job is to announce intent on the window:

The persistent player subscribes to that same window event in its connect() and is the only thing that ever owns audio:

This is the architectural hinge. The page is free to re-render, morph, get torn down and rebuilt — every track row controller is created and destroyed at will — because none of them hold any audio state. They are pure producers of spindle:play events. Exactly one long-lived consumer, the permanent player, holds the AudioContext and the transport state. The event bus is what lets those two lifecycles run at completely different speeds: ephemeral page, eternal player.

What rides in event.detail is the server's contribution to the whole feature. Each row serializes track.play_payload.to_json into a Stimulus value. That payload is the musical score the client needs and nothing more:

No audio URL, because there is no audio file. roots is a comma-separated string of MIDI note numbers (the seed data stores values like "57,53,60,55"), bpm sets the tempo, and texture — one of keys, pad, pluck, beat — tells the synth which arrangement to play. The server ships a score; the client is the instrument.

04 / THE ENGINEA real Web Audio synthesizer in one controller

This is the technical centerpiece, so it is worth being precise. The player does not play files — it builds a synthesizer with the Web Audio API and plays chord progressions live.

One graph, built lazily, only on a user gesture

The audio graph is created once, the first time the user actually triggers sound, and never re-built. The lazy guard at the top of #ensureAudio (if (this.ctx) return) makes it idempotent:

The signal path is oscillators → lowpass filter → master gain → destination, with a parallel feedback-delay send (delay → feedback → delay forms the regenerating echo, tapped through wet back into the master). The lowpass at 1.9 kHz keeps the timbre soft; the 0.34 s delay with 0.24 feedback gives the late-night, dubby tail the album moods advertise. Crucially this whole graph is built only inside #ensureAudio, which is called from load() and play() — both reached only through a user action. Nothing constructs an AudioContext on page load. The synth also resumes a suspended context on play (if (this.ctx.state === "suspended") this.ctx.resume()), which is the standard handshake for browser autoplay policies: audio begins only in response to a real gesture.

A lookahead scheduler, because setTimeout can't keep musical time

Web Audio's clock (ctx.currentTime) is sample-accurate, but JavaScript timers are not — setTimeout and setInterval drift by milliseconds under load, and milliseconds are audible as timing jitter. The correct pattern, and the one Spindle uses, is a lookahead scheduler: a coarse JS timer wakes up frequently and schedules notes a little way into the future against the precise audio clock, so the actual note onsets are governed by the audio hardware, not the timer.

The setInterval fires every 25 ms and, on each tick, schedules every beat whose start time falls within the next 120 ms window. Because the timer interval (25 ms) is comfortably shorter than the lookahead horizon (120 ms), there is always slack: even if a tick is late, the notes it was responsible for were already queued on a previous, earlier tick. The JS timer only has to be approximately on time; the audio engine plays everything exactly on time. This is the classic "A Tale of Two Clocks" approach and it is what separates glitch-free Web Audio sequencing from naive setTimeout playback.

Notes are oscillators with envelopes; chords are open and consonant

Each scheduled beat resolves a root note from the progression and voices it as an open fifth plus the octave, then layers a per-texture arrangement on top:

The fixed intervals of +7 (a perfect fifth) and +12/+19 (octaves) mean the harmony is always consonant no matter which roots a track ships — there are no thirds to turn major or minor, so any sequence of MIDI roots in the seed data produces something pleasant. texture selects the arrangement: pad holds a long four-beat sine chord with a slow 0.9 s attack; pluck uses a bright sawtooth with a near-instant attack; keys plays a softer triangle chord each beat; and beat adds rhythm. Every note is one oscillator wrapped in an ADSR-style gain envelope built from scheduled ramps:

The MIDI-to-frequency conversion is the standard equal-temperament formula; a small random detune of ±3 cents keeps stacked oscillators from sounding sterile. The envelope ramps up over attack and decays exponentially to silence by dur — and the oscillator is stopped just after, so spent nodes are garbage-collected rather than accumulating. The beat texture also gets a synthesized kick drum from #kick, a single oscillator whose pitch sweeps from 130 Hz down to 45 Hz in 120 ms with a fast gain decay — a classic synth-kick recipe, no sample required.

The progress bar comes from the beat counter

There is no audio element to read a currentTime from, so the progress bar is driven purely by the sequencer's own beat position — computed inline in #scheduleBeat from the bar and beat indices and written to the permanent element's bar target. The visual progress and the audio share one source of truth: the beat counter the scheduler is already advancing.

05 / WHY THESE CHOICES ARE GOODThe shape of the design

  • Zero audio assets. Procedural synthesis means the entire feature ships no MP3s, no CDN, no Active Storage — the payload is the small JSON score in each track row. The browser is the instrument.
  • A single audio graph owned by a permanent controller. Because #ensureAudio is guarded and the host element never re-mounts, there is exactly one AudioContext for the life of the session — no leaked contexts, no overlapping graphs, no double playback.
  • User-gesture-gated. The context is constructed and resumed only on a real interaction, so the app is compliant with browser autoplay policies by construction rather than by patching around them.
  • The server stays simple. Rails provides only the score — Track#play_payload — and the client synthesizes. The controller is two read-only actions; there is no media pipeline to operate.

06 / WHY IT MATTERS FOR CLIENTSPersistent UI without an SPA

"State that survives navigation" is one of the headline reasons teams adopt a single-page framework. A music player is the obvious example, but the same shape shows up everywhere in real products: a call/softphone widget that must not drop when an agent opens a record, a shopping cart drawer, a multi-step wizard, a live countdown timer, a media uploader mid-progress. The conventional answer is "make the whole app a SPA so the page never unloads." That is a large, expensive commitment to take on for one persistent widget.

Spindle demonstrates the cheaper answer. With data-turbo-permanent, Hotwire gives you genuinely persistent UI on top of ordinary server-rendered pages — the rest of the app keeps morphing freely, full navigation, fast page loads, no client router to maintain, while one designated node and its controller live on. The decoupling via a window CustomEvent is the reusable lesson: keep the long-lived state in the permanent element, let everything else be disposable, and let them communicate over an event bus. That pattern transfers directly to a client's call widget or cart.

The Web Audio engine is here to make a second point: this is depth past CRUD. The lookahead scheduler, the lazily-built graph, the envelope shaping, the autoplay-policy handshake — these are the details that separate someone who has read about Web Audio from someone who has shipped it. For hiring and maintainability that matters: the whole feature is one well-commented Stimulus controller and a model method, readable end-to-end in an afternoon, with no build step beyond importmap.

07 / HONEST TRADE-OFFSWhat this is and isn't

For production, know the edges

Procedural audio is a demo device, not a streaming product. Real catalogs need actual recordings, which means Active Storage or a streaming backend, range requests, and an <audio> element — a different feature. Spindle synthesizes specifically so the showcase has no asset dependency; the persistent-element pattern it proves is what transfers, not the synth.

  • Web Audio has browser quirks. The code handles the obvious ones — webkitAudioContext fallback, resuming a suspended context — but Web Audio behavior across browsers and especially mobile (where contexts can be reclaimed in the background) always needs real-device testing before shipping.
  • The permanent-element constraint is strict. It only works if the node has a stable id and appears on every destination page — which is exactly why the player is rendered from the layout, not a page template. Move it into a per-page partial and the guarantee evaporates. It is a sharp tool that must be wielded deliberately.
  • One persistent player, one stream. The design assumes a single owner of audio; it is not built for multiple independent players on screen at once. For Spindle's purpose that is the right scope, but it is a boundary worth naming.

Spindle is small on purpose. Two models, a two-action controller, two Stimulus controllers, and a window event between them — and out of that falls a player that keeps going as you browse the entire app. The lesson Levelbrook keeps coming back to with Hotwire is this one: the behaviors that look like they demand a SPA usually demand a single well-placed primitive instead. data-turbo-permanent is one of them.
